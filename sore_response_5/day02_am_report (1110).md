## 2교시 · 알림에 대상의 재직 · VIP · 접속 IP 맥락 붙이기

### 문제 2-1 · 알림 5건에 재직 · VIP · 접속 IP 맥락 붙이기

- (가) 실행한 출력 전체를 붙여 넣고, 재직 여부가 「퇴사」인 알림과 VIP 가 「예」인 알림의 번호, 단계 3 의 VIP 계정 알림 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 재직 여부가 「퇴사」인 알림 번호 ③ VIP 가 「예」인 알림 번호 ④ 단계 3 의 VIP 계정 알림 수
  - 답: 퇴사 알림은 `INC-001`, VIP 알림은 `INC-003`이고 VIP 알림은 1건입니다.

```
--- 단계 1: 불러온 알림 5 건 · 계정 정보 6 명 · 신뢰 IP 1 개
--- 단계 2: 알림마다 붙인 정보(재직 · VIP · 접속 IP)
INC-001 dami · 재직: 퇴사 · VIP: 아니오 · 접속 IP: 없음 · 신뢰 IP: 아니오
INC-002 seoyeon · 재직: 재직 · VIP: 아니오 · 접속 IP: 203.0.113.80 · 신뢰 IP: 예
INC-003 gaeun · 재직: 재직 · VIP: 예 · 접속 IP: 198.51.100.77 · 신뢰 IP: 아니오
INC-004 jiwoo · 재직: 재직 · VIP: 아니오 · 접속 IP: 203.0.113.80 · 신뢰 IP: 예
INC-005 198.51.100.90 · 재직: 계정 아님 · VIP: 아니오 · 접속 IP: 없음 · 신뢰 IP: 아니오
--- 단계 3: VIP 계정 알림 수
VIP 계정 알림 1 건
```

- (나) 🔍 INC-005 는 맥락이 모두 처음 값(`False` · `None`)으로 남았습니다. 왜 그렇게 나왔는지 `lookup_account` 와 `lookup_source_ip` 의 `if` 조건을 근거로 적어 주세요. 또 INC-005 의 `employed` 가 `True`(재직)로 나온다면 어떤 문제가 생길지도 적어 주세요.
  - 쓸 내용: ① INC-005 의 맥락이 모두 처음 값으로 남은 이유(어느 함수의 어느 `if` 조건 때문인지) ② 모르는 대상이 「재직」으로 나오면 생길 문제
  - 답: INC-005의 대상 `198.51.100.90`은 계정 정보나 접속 IP 파일에 키로 없습니다. 그래서 `lookup_account`의 `if entity in users_info`와 `lookup_source_ip`의 `if entity in source_ips`가 모두 거짓이고, 초기값인 `False`와 `None`이 그대로 남습니다. 이를 재직(`True`)으로 표시하면 계정이 아닌 IP를 정상 재직자로 오해해 뒤의 대응 판단이 잘못될 수 있습니다.

- (다) 🔍 INC-002 와 INC-004 는 접속 IP 가 같고 둘 다 「신뢰 IP: 예」입니다. 두 알림의 `reasons`(알림이 난 이유인 탐지 규칙 이름 목록)를 비교해 보세요. 접속 IP 가 같은 신뢰 IP 라는 이유만으로 두 알림을 똑같이 처리해도 되는지 적어 주세요.
  - 쓸 내용: ① 두 알림의 `reasons` ② 맥락만 보고 같게 처리해도 되는지와 그 이유
  - 답: INC-002의 규칙은 `평소와 다른 IP`와 `대량 다운로드`이고, INC-004는 `업무 시간 밖 로그인`과 `평소와 다른 IP`입니다. 둘 다 같은 신뢰 IP에서 왔더라도 대량 다운로드는 IP와 무관한 별도 행동이므로 같은 방식으로 처리하면 안 됩니다. 신뢰 IP라는 정보만으로 INC-002까지 정상으로 볼 수는 없습니다.

## 3교시 · 맥락을 보고 승인 필요 · 오탐 종료 · 기본 경로로 나누기

### 문제 3-1 · VIP 는 승인 경로로, 신뢰 IP 의 IP 관련 알림은 오탐으로 종료하기

- (가) 실행한 출력 전체를 붙여 넣고, 경로별 건수와 `종료` 상태가 된 알림의 번호를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 경로별 건수 ③ `종료` 상태가 된 알림 번호
  - 답: 기본 3건, 승인 필요 1건, 오탐 종료 1건입니다. 종료된 알림은 INC-004입니다.

```
--- 단계 1: 알림마다 정한 처리 경로 · 이유 · 상태
INC-001 dami high -> 기본 · 플레이북 기본 절차대로 처리함 (상태: 탐지됨)
INC-002 seoyeon mid -> 기본 · 플레이북 기본 절차대로 처리함 (상태: 탐지됨)
INC-003 gaeun mid -> 승인 필요 · VIP 계정이라 담당자 승인이 필요함 (상태: 탐지됨)
INC-004 jiwoo mid -> 오탐 종료 · 신뢰 IP에서 온 IP 관련 규칙뿐이라 정상 접속으로 봄 (상태: 종료)
INC-005 198.51.100.90 low -> 기본 · 플레이북 기본 절차대로 처리함 (상태: 탐지됨)
--- 단계 2: 경로별 건수
기본 3 건
승인 필요 1 건
오탐 종료 1 건
```

- (나) 🔍 INC-002 와 INC-004 는 둘 다 신뢰 IP 에서 접속했는데 INC-002 는 `기본`, INC-004 는 `오탐 종료` 입니다. 두 알림의 `reasons` 를 근거로 경로가 갈린 이유를 적어 주세요.
  - 쓸 내용: ① 두 알림의 `reasons` ② 경로가 갈린 이유
  - 답: INC-002는 `평소와 다른 IP`와 `대량 다운로드`가 걸렸고, INC-004는 `업무 시간 밖 로그인`과 `평소와 다른 IP`가 걸렸습니다. INC-002에는 IP 관련이 아닌 대량 다운로드가 포함되어 있어 모든 규칙이 IP 관련이라는 조건을 만족하지 않아 기본 경로로 갑니다. INC-004는 두 규칙이 모두 IP 관련이고 접속 IP도 신뢰 목록에 있어 오탐 종료됩니다.

- (다) 🔍 6번 조건을 확인하기 전에 4번 VIP 확인을 먼저 두었습니다. VIP 계정이 신뢰 IP 에서 접속했고 `평소와 다른 IP` 규칙 하나만 걸렸다고 해 봅시다. 이 알림이 어느 경로로 가는지 적어 주세요. 그리고 4번과 6번 조건의 순서를 바꾸면 무엇이 달라지는지 적어 주세요.
  - 쓸 내용: ① 그 VIP 알림이 가는 경로 ② 두 조건의 순서를 바꾸면 달라지는 점
  - 답: VIP 조건을 먼저 확인하므로 그 알림은 `승인 필요` 경로로 갑니다. 순서를 바꿔 신뢰 IP 조건을 먼저 검사하면 `오탐 종료`가 되어 VIP 알림이 담당자 확인 없이 닫힐 수 있습니다. 그래서 더 중요한 VIP 여부를 먼저 검사해야 합니다.

## 4교시 · 같은 알림을 두 번 처리하지 않고 한 번에 잠글 수 있는 계정 수 제한하기

### 문제 4-1 · 중복 실행을 막고 한 번에 잠글 수 있는 계정을 3개로 제한하기

- (가) 실행한 출력 전체를 붙여 넣고, 단계 1 · 3 · 4 의 잠긴 계정과 티켓 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 단계 1 · 3 · 4 의 잠긴 계정 ③ 단계 1 · 3 의 티켓 수
  - 답: 단계 1은 잠긴 계정 `['dami', 'dami']`, 티켓 2건입니다. 단계 3은 `['dami']`, 티켓 1건입니다. 단계 4는 `['dami', 'seoyeon', 'gaeun']` 3개를 잠갔고 티켓은 7건입니다.

```
--- 단계 1: 어제 방식(안전장치 없음)으로 같은 알림 5건을 두 번 처리
잠긴 계정: ['dami', 'dami']
티켓: 2 건

잠긴 계정 7 개: ['dami', 'dami', 'seoyeon', 'gaeun', 'jiwoo', 'junho', 'hana']
--- 단계 3: 안전한 방식으로 같은 알림 5건을 두 번 처리
첫 번째 처리
INC-001 dami -> 실행 완료 (상태: 조치됨)
INC-002 seoyeon -> 승인 대기 (상태: 분류됨)
INC-003 gaeun -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-004 jiwoo -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-005 198.51.100.90 -> 승인 대기 (상태: 분류됨)
두 번째 처리
INC-001 dami -> 이미 처리됨 (상태: 조치됨)
INC-002 seoyeon -> 승인 대기 (상태: 분류됨)
INC-003 gaeun -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-004 jiwoo -> 맞는 플레이북 없음 (상태: 탐지됨)
INC-005 198.51.100.90 -> 승인 대기 (상태: 분류됨)
```

- (다) 🔍 단계 4 에서 잠긴 계정 3개 가운데 `users_info.json` 의 `employed` 로 볼 때 잘못 잠긴 계정이 있는지 적고, 한도가 없을 때와 비교해 잘못 잠긴 계정이 몇 개 줄었는지 적어 주세요. 한도로 막지 못한 문제가 무엇인지도 적어 주세요. 마지막으로, 2교시의 맥락과 3교시의 경로 중 무엇을 쓰면 잘못 잠긴 계정을 줄일 수 있는지 적어 주세요.
  - 쓸 내용: ① 잘못 잠긴 계정 ② 한도가 없을 때와 비교한 피해 ③ 한도가 막지 못한 문제 ④ 줄이는 방법
  - 답: 단계 4에서 잠긴 `seoyeon`과 `gaeun`은 `users_info.json`에서 재직자로 표시되어 잘못 잠겼습니다. 중복 방지만 적용하고 한도가 없으면 서로 다른 계정 6개가 잠겨 실제 퇴사자 dami를 제외한 5명이 잘못 잠깁니다. 3개 한도로 잘못 잠긴 계정은 5명에서 2명으로 줄었지만, 한도는 잘못된 알림 자체를 판별하지 못합니다. 2교시에서 붙인 재직 여부 맥락을 잠금 전에 확인하면 재직자는 제외할 수 있고, VIP인 gaeun은 3교시의 승인 필요 경로로 보내 추가로 보호할 수 있습니다.
