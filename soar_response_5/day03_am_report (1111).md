# 5과목 Day 2 계정 잠금 · IP 차단 · 세션 종료 · 오전 (이름 · 2026-11-11(수))

## 2교시 · 계정 잠금 · 사후 검증 · 감사 기록

### 문제 2-1

- (가) 실행 출력:

```
--- 단계 1: 조치 전에 잠겨 있는 계정
['junho']
--- 단계 2: 잠금 요청 3건
INC-001 dami · 잠기지 않음 → 잠김 · 퇴사한 계정의 서버 요청
INC-003 gaeun · 변경 없음 → 변경 없음 · VIP 계정이라 자동 조치 대상이 아님
INC-006 junho · 잠김 → 잠김 · 이미 잠겨 있어 변경 없음
--- 단계 3: 오탐으로 확인되어 dami 해제
INC-001 dami · 잠김 → 잠기지 않음 · 오탐으로 확인되어 해제
--- 단계 4: 파일에 저장된 값 다시 읽기
잠긴 계정: ['junho']
조치 기록: 4 건
```

단계 4의 잠긴 계정은 `['junho']`, 조치 기록은 4건입니다.

- (나) 단계 2에서 INC-003 `gaeun`은 `변경 없음 → 변경 없음 · VIP 계정이라 자동 조치 대상이 아님`으로 기록됐습니다. `gaeun`이 VIP 목록에 포함되어 있어 `check_policy`가 자동 잠금을 거부했기 때문입니다. 앞선 경로 분기만 믿으면 설정 오류가 있거나 다른 코드가 조치 함수를 직접 호출할 때 정책을 우회할 수 있습니다. 조치 함수에서도 다시 검사하면 한 단계의 통제가 빠져도 다른 단계가 막는 심층 방어가 됩니다.

- (다) `before`가 있으면 조치 전부터 잠겨 있던 `junho`와 이번 대응에서 새로 잠근 계정을 구별할 수 있습니다. 따라서 롤백 때 자동 대응으로 상태가 바뀐 계정만 해제하고, 원래 잠겨 있던 계정은 유지할 수 있습니다. `verify_locked`가 없으면 실제 잠금이 실패했어도 성공한 것으로 기록될 수 있습니다. 사후 검증은 실제 상태를 확인해 이런 불일치를 `잠기지 않음 (확인 실패)`로 드러냅니다.

## 3교시 · 허용 목록 · 공유 IP · TTL

### 문제 3-1

- (가) 실행 출력:

```
--- 단계 1: 차단 요청 3건
INC-005 198.51.100.90 · 차단되지 않음 → 차단됨 · 경로 스캔 (120분 뒤 자동 해제)
INC-009 192.0.2.10 · 변경 없음 → 변경 없음 · 허용 목록 IP 라서 차단하지 않음
INC-008 192.0.2.41 · 변경 없음 → 변경 없음 · 여러 계정이 함께 쓰는 IP 라서 담당자 승인 필요
--- 단계 2: 차단 뒤 차단한 IP 와 끝나는 시각
차단한 IP: ['198.51.100.90']
차단이 끝나는 시각(분): {'198.51.100.90': 120}
--- 단계 3: 시계를 120분 뒤로 옮기고 시간이 끝난 차단 풀기
INC-005 198.51.100.90 · 차단됨 → 차단되지 않음 · 차단 시간이 끝나 자동 해제
차단한 IP: []
--- 단계 4: 파일에 저장된 값 다시 읽기
차단한 IP: []
조치 기록: 4 건
```

실제 차단된 IP는 `198.51.100.90`입니다. `192.0.2.10`은 허용 목록에 있어 차단하지 않았고, `192.0.2.41`은 여러 계정이 공유해 담당자 승인 대상으로 남겼습니다.

- (나) `ip_users.json`에서 `192.0.2.41`을 사용하는 계정은 `junho`와 `hana` 두 명입니다. 사용 계정 수가 공유 IP 기준인 2명 이상이므로 자동 차단하지 않았습니다. 그대로 차단했다면 두 사용자가 모두 해당 IP를 통한 업무 접속을 할 수 없게 되어 정상 사용자에게도 서비스 중단이 발생할 수 있습니다.

- (다) 단계 2에서 `198.51.100.90`의 만료 시각은 120이고, 단계 3에서 시계를 120으로 이동했습니다. `end_time <= state["clock"]` 조건이 참이 되어 차단이 자동 해제됐습니다. 임시 차단은 오래된 차단이 계속 남는 일을 막고 정상 서비스의 가용성을 회복합니다. 영구 차단은 사유와 영향을 사람이 확인한 뒤 결정할 수 있습니다.

## 4교시 · 계정 잠금 · 세션 종료 · 사후 점검

### 문제 4-1

- (가) 실행 출력:

```
--- 단계 1: 점검 - 잠겼는데 세션이 열려 있는 계정
['junho']
--- 단계 2: 잠금 → 세션 종료
INC-001 dami · 잠기지 않음 → 잠김 · 퇴사한 계정의 서버 요청
INC-001 dami · 세션 2개 → 세션 0개 · 퇴사한 계정의 서버 요청
INC-003 gaeun · 변경 없음 → 변경 없음 · VIP 계정이라 자동 조치 대상이 아님
INC-006 junho · 잠김 → 잠김 · 이미 잠겨 있어 변경 없음
INC-006 junho · 세션 1개 → 세션 0개 · 퇴사 처리 확인
--- 단계 3: 조치 뒤 다시 점검
빈틈이 남은 계정: []
잠긴 계정: ['junho', 'dami']
--- 단계 4: 파일에 저장된 값 다시 읽기
잠긴 계정: ['junho', 'dami']
조치 기록: 5 건
```

단계 3에서 빈틈이 남은 계정은 `[]`, 단계 4의 잠긴 계정은 `['junho', 'dami']`입니다.

- (나) `junho`는 실습 전부터 잠겨 있었지만 세션 `S-501`이 열려 있어 1단계 점검에서 발견됐습니다. `dami`는 단계 2에서 계정 잠금과 세션 종료(세션 2개 → 0개)를 받았습니다. 잠금만 했다면 `S-101`, `S-102` 세션이 유효하게 남아 그 세션을 이용한 접속이 계속 가능했을 것입니다.

- (다) `gaeun`의 단계 2 기록은 `변경 없음 → 변경 없음 · VIP 계정이라 자동 조치 대상이 아님`입니다. 따라서 `lock_record["after"] == "잠김"` 조건이 거짓이어서 세션 종료 단계도 실행되지 않았습니다. 잠금이 적용되지 않은 계정의 세션을 종료하면 정상 사용자의 접속만 끊고 재로그인은 여전히 허용하는 불완전한 조치가 됩니다. 특히 VIP 계정은 승인 전 업무 중단을 일으킬 수 있으므로 세션 종료를 해서는 안 됩니다.
