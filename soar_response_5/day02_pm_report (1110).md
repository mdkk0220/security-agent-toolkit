## 5교시 · 담당자의 승인 · 거절 결정을 적용하고, 권한 없는 승인은 막기

### 문제 5-1 · 감사 기록을 만들고, 권한을 확인해 담당자 결정을 적용하기

- (가) 실행한 출력 전체를 붙여 넣고, 처리 뒤 티켓 수 · 담당자 알림 수 · `분류됨` 으로 남은 알림의 번호를 각각 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 처리 뒤 티켓 수 ③ 담당자 알림 수 ④ `분류됨` 으로 남은 건의 번호
  - 답: 티켓은 1건, 담당자 알림은 1건입니다. `분류됨`으로 남은 건은 권한 없는 승인 시도가 거부된 INC-005입니다.

```
--- 단계 1: 승인 대기 건
INC-002 seoyeon · PB-002 · 플레이북 승인 값이 담당자 승인 필요
INC-003 gaeun · VIP 확인 · VIP 계정이라 경로가 승인 필요
INC-005 198.51.100.90 · PB-003 · 플레이북 승인 값이 담당자 승인 필요
--- 단계 2: 담당자 결정 처리
INC-002 seoyeon -> 실행 완료 (상태: 조치됨)
INC-003 gaeun -> 거절 처리 (상태: 종료)
INC-005 198.51.100.90 -> 권한 없음 (상태: 분류됨)
--- 단계 3: 처리 뒤 모의 시스템 상태
잠긴 계정: []
차단한 IP: []
티켓: 1 건 · 담당자 알림: 1 건
--- 단계 4: 감사 기록
INC-002 PB-002 담당자 알림 : 담당자 알림 전송 (승인: kim.sec)
INC-002 PB-002 티켓 생성 : 티켓 TCK-1 생성 (승인: kim.sec)
INC-003 VIP 확인 전체 : 거절됨 (승인: kim.sec — 계정 관리자의 정상 작업으로 확인됨)

```

- (나) 🔍 INC-005 는 결정이 `승인` 인데 실행되지 않았습니다. 단계 2 와 단계 4 의 출력을 근거로 그 이유를 적어 주세요. 그리고 권한 확인이 없을 때 생길 위험도 적어 주세요.
  - 쓸 내용: ① INC-005 가 실행되지 않은 이유(단계 2 · 4 의 출력 근거) ② 이 확인이 없을 때 생길 위험
  - 답: INC-005는 `승인` 결정이지만 approver인 `intern01`이 승인 권한 목록에 없어 실행되지 않았습니다. 단계 2에는 `권한 없음 (상태: 분류됨)`, 단계 4에는 `권한 없음 — 승인 시도: intern01`이 기록되고, 단계 3의 `차단한 IP: []`로 차단이 실행되지 않았음을 확인할 수 있습니다. 권한 확인이 없으면 권한 없는 사람이 승인만 눌러도 IP 차단이 진행되어, 같은 IP를 쓰는 정상 사용자의 업무까지 막을 수 있습니다.

- (다) 🔍 INC-003 이 승인 대기가 된 이유(단계 1), 거절된 뒤의 상태, 감사 기록에 남은 내용을 각각 적어 주세요.
  - 쓸 내용: ① 단계 1 의 승인 대기 이유 ② 거절된 뒤 INC-003 의 상태 ③ 감사 기록에 남은 내용
  - 답: INC-003은 VIP 계정이라 오전 경로 분기에서 담당자 확인이 필요해 승인 대기 상태가 됐습니다. 담당자 kim.sec가 정상 작업으로 확인해 거절했고, 상태는 `종료`가 됐습니다. 감사 기록에는 `거절됨 (승인: kim.sec — 계정 관리자의 정상 작업으로 확인됨)`이 남아 누가 어떤 이유로 종료했는지 확인할 수 있습니다.

## 6교시 · 연결 오류가 나면 최대 3번 시도하고, 실패한 건을 목록으로 모으고, 오늘 만든 하루 흐름 전체 읽기

### 문제 6-1 · 연결 오류가 나면 최대 3번 시도하고, 실패한 건을 목록으로 모으기

- (가) 실행한 출력 전체를 붙여 넣고, 단계 3 에서 `일부 실패` · `승인 대기` · `오탐 종료`(오탐: 위험하지 않은데 위험하다고 잘못 알린 경우) 인 알림의 번호를 각각 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② `일부 실패` 인 알림 번호 ③ `승인 대기` 인 알림 번호 ④ `오탐 종료` 인 알림 번호
  - 답: 일부 실패는 INC-001, 승인 대기는 INC-002 · INC-003 · INC-005, 오탐 종료는 INC-004입니다.

```
--- 단계 1: 일시 장애 — 티켓 서비스가 2번 실패한 뒤 복구
티켓 TCK-1 생성 (시도 3회)
만든 티켓: 1 건
--- 단계 2: 서비스 중단 — 티켓 서비스가 계속 실패
실패: 연결 실패: 티켓 생성 서비스가 응답하지 않음 (3회 모두 실패)
만든 티켓: 0 건
--- 단계 3: 하루 흐름 — 티켓 서비스가 계속 실패하는 상황
INC-001 dami -> 일부 실패 (상태: 분류됨)
INC-002 seoyeon -> 승인 대기 (상태: 분류됨)
INC-003 gaeun -> 승인 대기 (상태: 분류됨)
INC-004 jiwoo -> 오탐 종료 (상태: 종료)
INC-005 198.51.100.90 -> 승인 대기 (상태: 분류됨)
--- 단계 4: 담당자 결정 처리
INC-002 seoyeon -> 실행 완료 (상태: 조치됨)
INC-003 gaeun -> 거절 처리 (상태: 종료)
INC-005 198.51.100.90 -> 권한 없음 (상태: 분류됨)
--- 단계 5: 하루가 끝난 뒤 모의 시스템 상태
잠긴 계정: ['dami']
차단한 IP: []
티켓: 1 건 · 담당자 알림: 1 건
--- 단계 6: 담당자 확인이 필요한 건
INC-001 티켓 생성 : 실패: 연결 실패: 티켓 생성 서비스가 응답하지 않음 (3회 모두 실패)
INC-005 승인 대기 : 플레이북 승인 값이 담당자 승인 필요
```

- (나) 🔍 단계 1 과 2 는 같은 `run_with_retry` 인데 결과가 다릅니다. 두 단계의 `fail_plan` 값을 근거로 이유를 적어 주세요. 그리고 최대 횟수가 없으면 서비스가 계속 멈춰 있을 때 어떤 문제가 생기는지도 적어 주세요.
  - 쓸 내용: ① 단계 1 과 2 의 `fail_plan` 값 ② 결과가 달라진 이유 ③ 최대 시도 횟수가 없을 때의 문제
  - 답: 단계 1의 실패 계획은 `{"INC-001|티켓 생성": 2}`여서 두 번 실패한 뒤 세 번째 시도에서 티켓 생성이 성공했습니다. 단계 2는 같은 액션이 `99`번 실패하도록 설정했으므로 허용된 세 번 모두 실패했습니다. 최대 횟수 제한이 없으면 장애가 계속되는 동안 재시도가 끝나지 않아 프로그램이 멈추고 다른 알림 처리도 지연될 수 있습니다.

- (다) 🔍 단계 3 에서 INC-001 은 계정은 잠겼는데 상태가 `조치됨` 이 아닙니다. 그 이유를 적어 주세요. 또 단계 6 의 출력이 담당자에게 무엇을 알려 주는지 적어 주세요. 마지막으로, 같은 `state` 로 다시 처리해도 `dami` 가 두 번 잠기지 않는 이유를 오전 4교시에서 만든 장치와 연결해 적어 주세요.
  - 쓸 내용: ① INC-001 이 `조치됨` 이 아닌 이유 ② 단계 6 이 담당자에게 알려 주는 것 ③ 다시 실행해도 `dami` 가 두 번 잠기지 않는 이유
  - 답: INC-001은 계정 잠금은 성공했지만 티켓 생성이 최대 세 번 모두 실패해 `일부 실패`로 남았습니다. 모든 액션이 성공하지 않았으므로 상태를 `조치됨`으로 바꾸지 않고 `분류됨`에 둡니다. 단계 6의 실패 기록은 담당자에게 티켓이 생성되지 않았고 연결 오류로 재시도도 소진됐음을 알립니다. 같은 `state`로 다시 실행해도 오전 4교시의 `safe_run_action`이 이미 잠긴 dami를 `건너뜀: 이미 잠겨 있음`으로 처리하므로 계정 잠금이 중복되지 않습니다.
