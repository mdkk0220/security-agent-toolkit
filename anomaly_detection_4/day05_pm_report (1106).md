## 5교시 · 도커 복습 · 컴포즈로 서버 두 대 한 번에 켜기

### 문제 5-1 · 서버 한 대를 복습하고 컴포즈로 두 대 켜기

- (가) 5교시 순서의 서버 켜기 · 확인 명령(`docker images` 부터 `curl` 까지)과 그 결과를 친 순서대로 붙여 넣고, 서비스 이름 두 개와 각 서비스의 포트를 적어 주세요.
  - 쓸 내용: ① 명령과 결과를 친 순서대로(코드 상자에 붙여 넣기): `docker images` · `docker run` · `docker ps` · `docker stop` · `docker compose up -d` · `docker compose ps` · `curl` 두 개 (`docker pull` 은 받았을 때만, `pwd` · `touch` · `ls` 는 붙이지 않아도 됩니다) ② 서비스 이름 두 개 ③ 각 서비스의 포트
  - 답: 이 실행 환경에는 Docker CLI가 없어 실제 명령은 실행하지 못했습니다. 아래는 안내서의 정상 실행 예시이며 실제 실행 출력은 아닙니다. 서비스는 `web1`(호스트 8080 → 컨테이너 80), `web2`(호스트 8081 → 컨테이너 80)입니다.

```
$ docker images nginx:1.28
nginx:1.28 이미지가 있으면 docker pull은 생략
$ docker run -d --rm -p 8080:80 --name web-run nginx:1.28
컨테이너 ID 출력
$ docker ps
web-run   nginx:1.28   Up   0.0.0.0:8080->80/tcp
$ docker stop web-run
web-run
$ docker compose up -d
web1 · web2 컨테이너 Started
$ docker compose ps
web1   nginx:1.28   Up   0.0.0.0:8080->80/tcp
web2   nginx:1.28   Up   0.0.0.0:8081->80/tcp
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080
200
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8081
200
```

- (나) 🔍 서버 두 대를 `docker run` 으로 켜는 것과 `compose.yaml` 과 `docker compose up -d` 로 켜는 것을 비교해, 컴포즈가 더 나은 점을 두 가지 적어 주세요.
  - 쓸 내용: ① 컴포즈가 더 나은 점 두 가지
  - 답: 포트·이미지·재시작 정책 같은 설정을 `compose.yaml`에 기록해 다른 사람이 실행해도 같은 구성으로 켤 수 있습니다. 또 `docker compose up -d` 한 번으로 여러 서버를 함께 시작하고 상태도 한 파일 기준으로 관리할 수 있어, 긴 `docker run` 명령을 반복 입력하다 생기는 실수를 줄입니다.

- (다) 🔍 보안 사고가 난 뒤 감사팀이 「사고 당시와 같은 구성으로 서버를 다시 켜 보라」고 요청했습니다. 팀원 한 명은 3주 전에 긴 `docker run` 명령을 직접 쳐서 서버를 켰는데 그 명령을 기억하지 못합니다. 다른 팀은 `compose.yaml` 을 깃허브에 올려 두었습니다. 두 팀이 같은 구성을 다시 켤 수 있는지 비교하고, 파일에 `nginx:1.28` 처럼 버전을 적어 두는 것이 이런 재현에 왜 중요한지 적어 주세요.
  - 쓸 내용: ① 두 팀의 차이 ② 버전을 적어 두는 것이 재현에 중요한 이유
  - 답: `docker run` 명령만 사용한 팀은 옵션을 기억하거나 기록에서 찾아야 하므로 명령을 잃어버리면 구성을 정확히 재현하기 어렵습니다. 반면 Compose 파일을 GitHub에 보관한 팀은 파일과 이력을 확인해 `docker compose up -d`로 같은 설정을 다시 적용할 수 있습니다. `nginx:1.28`처럼 이미지 버전까지 고정해야 나중에 `nginx`의 최신 이미지가 달라져 동작·기본 설정이 바뀌는 일을 줄이고, 당시와 가까운 환경을 재현할 수 있습니다.

- (라) 🔍 팀원 세 명이 같은 `compose.yaml` 로 서버를 켰는데 한 명의 PC 에서만 `8081` 번 포트를 다른 프로그램이 쓰고 있어서 `web2` 가 켜지지 않았습니다. 이 사람이 파일의 어느 줄을 어떻게 바꾸면 되는지 적고, 바꿔도 서버 안에서는 여전히 `80` 번 포트로 동작하는 이유를 적어 주세요. 이 사람이 `curl` 로 확인할 때 달라지는 점도 적어 주세요.
  - 쓸 내용: ① 바꿀 줄과 바꾼 모양 ② 서버 안은 그대로 80 인 이유 ③ curl 주소의 달라지는 점
  - 답: `web2`의 `ports` 줄에서 호스트 포트인 왼쪽 `8081`만 사용하지 않는 번호로 바꿉니다. 예를 들어 `- "8082:80"`으로 바꿉니다. 오른쪽 `80`은 컨테이너 안 nginx가 듣는 포트라서 그대로 둡니다. 확인할 때는 `curl` 주소의 호스트 포트를 새 번호로 바꿔 `http://localhost:8082`에 요청합니다.

## 6교시 · 서버마다 접속 범위 정하기 · 설정 바꿔 적용하기

### 문제 6-1 · 서버마다 접속 범위를 정해 컴포즈 파일로 적용하기

- (가) 1번과 5번의 `docker compose ps` 출력을 붙여 넣고, 접속 범위가 바뀐 기존 서비스와 새로 추가된 서비스를 따로 적어 주세요.
  - 쓸 내용: ① 1번 출력(코드 상자에 붙여 넣기) ② 5번 출력(코드 상자에 붙여 넣기) ③ 접속 범위가 바뀐 기존 서비스 ④ 새로 추가된 서비스
  - 답: Docker를 실행할 수 없어 실제 `ps` 출력과 접속 로그를 만들지는 못했습니다. 아래는 안내서의 정상 결과 예시이며, `logs/web_404.log`도 안내서에 실린 예시 형식의 404 로그 두 줄로 채웠습니다(실제 컨테이너에서 수집한 로그는 아닙니다). 접속 범위가 바뀐 기존 서비스는 `web2`, 새로 추가된 서비스는 `web3`입니다.

```
① 적용 전: docker compose ps
SERVICE   STATUS   PORTS
web1      Up       0.0.0.0:8080->80/tcp
web2      Up       0.0.0.0:8081->80/tcp

⑤ 적용 후: docker compose -f compose.secure.yaml ps
SERVICE   STATUS   PORTS
web1      Up       0.0.0.0:8080->80/tcp
web2      Up       127.0.0.1:8081->80/tcp
web3      Up       127.0.0.1:8082->80/tcp
```

- (나) 🔍 `"8081:80"` 과 `"127.0.0.1:8081:80"` 은 누가 접속할 수 있는지가 어떻게 다른가요? 관리 화면이나 데이터베이스 서버를 이렇게 설정하는 이유도 적어 주세요.
  - 쓸 내용: ① 두 포트 줄에서 누가 접속할 수 있는지의 차이 ② 관리 화면 · 데이터베이스를 이렇게 설정하는 이유
  - 답: `"8081:80"`은 기본적으로 호스트의 모든 네트워크 인터페이스에 포트를 공개해 같은 네트워크의 다른 PC에서도 접속할 수 있습니다. `"127.0.0.1:8081:80"`은 호스트 루프백 주소에만 바인딩하므로 해당 PC에서만 접속할 수 있습니다. 관리 화면이나 데이터베이스는 외부에 불필요하게 노출하지 않고 필요한 사용자·시스템만 접근하게 제한해 무단 접근 위험을 줄여야 합니다.

- (다) 🔍 `up -d` 의 출력에서 `web1` 은 `Running`, `web2` 는 `Recreated`, `web3` 은 `Created` 였습니다. 서버마다 출력이 다른 이유와, 운영 중인 서비스의 설정을 바꿀 때 이것이 왜 도움이 되는지 적어 주세요.
  - 쓸 내용: ① 서버마다 출력이 다른 이유 ② 서버를 끊지 않고 바꿀 수 있는 것의 쓸모
  - 답: `web1`은 설정이 바뀌지 않아 기존 컨테이너를 그대로 사용해 `Running`이고, `web2`는 포트 바인딩 설정이 바뀌어 새 설정으로 컨테이너를 다시 만들어 `Recreated`입니다. `web3`은 새로 추가되어 `Created`입니다. 변경된 서비스만 재생성하면 설정을 반영하면서 바뀌지 않은 `web1`은 계속 실행할 수 있어 불필요한 중단을 줄입니다. 다만 재생성되는 서비스 자체에는 재시작이 발생할 수 있습니다.
