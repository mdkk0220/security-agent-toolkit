## 2교시 · 점수 파일의 사실만 Gemini API 에 보내 대상별 AI 요약 받기

### 문제 2-1 · AI 에게 사실만 보내 대상별 요약 받기

- (가) 실행한 출력 전체를 붙여 넣고, 요약한 대상 수와 `(요약 실패 …)` 가 나온 대상 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 요약한 대상 수 ③ `(요약 실패 …)` 가 나온 대상 수
  - 답: 외부 Gemini API에 샘플 로그 사실을 보내지 않고 `python pipeline.py --offline`으로 로컬 검증했습니다. 따라서 실제 AI 요약은 0개이고, 대상별 대체 문장은 5개입니다. 실행 결과는 다음과 같습니다.

```
이벤트 57개 · 탐지 규칙 8건
대상 기록 5건 · 요약 5건
요약 실패 0건 · 호출 생략 5건
day06_report.json 저장
```

- (나) 🔍 단계 3 의 지시문이 AI 에게 하지 말라고 한 것 두 가지를 찾고, 각각 하면 왜 위험한지 적어 주세요.
  - 쓸 내용: ① 하지 말라고 한 것 두 가지 ② 각각 하면 위험한 이유
  - 답: 점수 파일에 없는 사실이나 원인을 지어내지 말라고 했습니다. 없는 정보를 덧붙이면 담당자가 실제 로그에 없는 행동을 사실로 오해해 조사 방향을 잘못 잡을 수 있습니다. 또 점수와 규칙만으로 공격·침해라고 단정하거나 계정 차단 같은 조치를 지시하지 말라고 했습니다. 이 점수는 우선 확인할 대상을 정하는 신호이지 공격의 증거가 아니므로, 잘못 단정하면 정상 사용자를 막거나 실제 근거를 놓칠 수 있습니다.

- (다) 🔍 단계 4 의 요약 하나를 골라 2.1 의 점수 기록 표(대상 · 점수 · 등급 · 탐지된 규칙)와 비교해, 표에 없는 내용이 들어 있는지 적어 주세요. 있으면 어떤 문장인지와 지시문을 어떻게 고칠지, 없으면 없다고 쓰고 탐지된 규칙이 모두 문장에 들어갔는지 적어 주세요.
  - 쓸 내용: ① 고른 요약의 대상 ② 표에 없는 내용이 있는지 ③ 있으면 그 문장과 지시문을 고칠 방법, 없으면 탐지된 규칙이 모두 들어갔는지
  - 답: dami를 골랐습니다. 로컬 대체 문장은 “AI 호출 생략 — dami는 60점(high)이며, 탐지 규칙은 퇴사한 계정입니다.”입니다. 앞의 호출 생략 표시는 실행 상태이고, 요약 내용은 2.1 표의 대상·점수·등급·규칙과 일치합니다. 표에 없는 사실은 없고, 탐지된 규칙도 모두 들어갔습니다. 다만 이 문장은 Gemini 응답이 아니라 API 호출을 생략했을 때 코드가 만든 대체 문장입니다.

## 3교시 · 탐지부터 보고서 저장까지 pipeline.py 로 한 번에 실행하기

### 문제 3-1 · 읽기부터 보고서 저장까지 pipeline.py 로 실행하기

- (가) 실행한 출력 전체를 붙여 넣고, 보고서 파일의 `event_count` · `finding_count` 값과 `records` · `summaries` 의 건수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② `event_count` ③ `finding_count` ④ `records` 건수 ⑤ `summaries` 건수
  - 답: `python pipeline.py --offline` 실행 결과입니다. 보고서 파일은 `day06_report.json`입니다.

```
이벤트 57개 · 탐지 규칙 8건
대상 기록 5건 · 요약 5건
요약 실패 0건 · 호출 생략 5건
day06_report.json 저장
```

- (나) 🔍 점수와 등급은 코드가 정하고 AI 에게는 요약만 시킨 이유를 적어 주세요. 단계 5 의 확인할 순서와 단계 3 의 요약을 근거로 쓰세요.
  - 쓸 내용: ① 점수와 등급을 코드가 정한 이유 ② 단계 5 와 단계 3 에서 찾은 근거
  - 답: 점수와 등급은 정해진 규칙과 가중치로 계산되므로 코드가 정해야 결과가 일관되고 다시 검증할 수 있습니다. 단계 5에서 점수는 담당자가 확인할 순서를 정하는 데 쓰고 공격 여부를 확정하지 않는다고 했고, 단계 3에서도 AI는 점수 파일에 있는 사실을 요약할 뿐 새로운 사실이나 판단을 만들지 않도록 제한했습니다. 그래서 AI가 수치를 바꾸거나 사실처럼 추정을 보태지 않게 했습니다.

- (다) 🔍 AI 호출이 실패해도 파이프라인이 멈추지 않고 대체 문장을 쓰게 만든 이유를 적어 주세요. 대체 문장이 들어간 대상을 담당자가 어떻게 처리해야 하는지도 적어 주세요.
  - 쓸 내용: ① 실패해도 멈추지 않게 만든 이유 ② 대체 문장이 들어간 대상을 처리하는 방법
  - 답: API 키 누락·시간 초과·서버 오류가 나도 코드가 이미 만든 탐지 결과와 보고서 저장까지 끝내도록 해 결과 전체가 사라지지 않게 합니다. 대체 문장은 AI 요약이 아니라는 점을 확인하고, 대상·점수·탐지 규칙을 원본 이벤트와 대조해 사람이 직접 검토합니다. 자동 요약 실패를 정상 요약으로 오해하지 않도록 `status`와 실행 로그도 함께 확인해야 합니다.

## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1 · 2 · 3 · 4 · 7 · 8 중 4개 이상 씁니다. 상황 5 · 6 은 본보기입니다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 분류 규칙이 HTTP 실패를 먼저 일반 오류로 보거나 `/.env`, `/wp-login.php`, `/phpmyadmin` 같은 경로를 의심 규칙에 넣지 않았기 때문입니다. 한 줄씩 상태 코드만 보면 404 오류로 보입니다.
- 고칠 파일: `classify.py`
- 어떻게 고치나요: 일반 실패 규칙보다 먼저 알려진 민감 경로 패턴을 검사해 의심으로 분류합니다. 단, 모든 404를 의심으로 바꾸지는 않습니다.
- 고친 뒤 확인: `198.51.100.90`의 세 요청은 의심으로, `198.51.100.21`의 `/board/99` 한 건은 오류로 남는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택): 같은 IP의 요청 시각·경로·결과를 원본 로그에서 확인해 연속 탐색인지 살펴봅니다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인: 30줄 중 요청 형식이 깨진 두 줄은 `normalize_web`이 `None`으로 반환해 이벤트에 넣지 않았습니다. 샘플에서는 의도된 손상 줄이므로 28개가 정상 이벤트 수입니다.
- 고칠 파일: 원본 로그를 복구해야 한다면 로그 수집 경로, `normalize_web.py`와 `normalize.py`의 거부 건수 기록 부분
- 어떻게 고치나요: 깨진 줄을 정상 이벤트인 것처럼 만들지 말고 원본 로그에서 다시 수집합니다. 파서가 건너뛴 줄과 이유를 별도로 집계해 데이터 손실이 숨지 않게 합니다.
- 고친 뒤 확인: 입력 30줄, 정상 이벤트 28개, 형식 오류 2개가 각각 기록되고, 오류 원문을 다시 확인할 수 있는지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 원본 로그 보관본에서 두 줄이 실제 손상인지 수집 과정에서 잘렸는지 확인합니다.

#### 상황 3 · 웹 서버 로그에서 사용자를 알 수 있는 요청이 1개뿐
- 원인: 웹 이벤트에는 IP만 있고 사용자 ID가 없습니다. 성공한 SaaS 로그인에서 만든 IP-사용자 표와 일치한 웹 실패만 사용자 연결이 가능해, 현재 샘플에서는 1건만 연결됩니다.
- 고칠 파일: `correlation.py`
- 어떻게 고치나요: 가능하면 인증 프록시·세션 로그의 사용자 ID나 요청 ID를 웹 로그에 포함해 연결합니다. IP만으로 연결할 때는 시각 범위와 NAT·공유 IP 여부도 확인하고, 모르는 사용자를 임의로 채우지 않습니다.
- 고친 뒤 확인: 실제로 식별 가능한 요청만 사용자와 연결되고, 나머지는 사용자 미상으로 남는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택): 해당 시각의 인증·프록시 로그와 NAT 기록을 대조해 IP를 실제 사용자와 연결할 근거가 있는지 확인합니다.

#### 상황 4 · 두 로그에 나오는 seoyeon 이 연결되지 않음
- 원인: `correlation.py`는 서로 다른 로그가 2종류 이상이고 처음부터 마지막까지 60분 이내일 때 연결합니다. seoyeon은 로그 종류 조건은 만족하지만 전체 시간이 555분이라 시간 조건을 넘습니다.
- 고칠 파일: `correlation.py`
- 어떻게 고치나요: 하루 전체 시간을 억지로 60분 안으로 늘리지 않습니다. 필요하다면 사건별 시간 창을 굴리는 방식으로 연결해, 멀리 떨어진 별개 접속을 한 사건으로 합치지 않게 합니다.
- 고친 뒤 확인: 60분 안에 겹치는 관련 이벤트만 연결되고, 555분에 걸친 seoyeon 기록은 별도 사건으로 남는지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 서버·SaaS 로그의 정확한 시각과 시간대를 대조해 실제로 이어진 사건인지 확인합니다.

#### 상황 5 · 협력사 사무실에서 접속한 정상 접속에 알림이 남 (본보기)
- 원인: 규칙 문제입니다. `SaaS 평소와 다른 IP` 규칙은 지난 접속 기록에 없는 IP 이면 모두 알림을 냅니다. 협력사 사무실 IP 203.0.113.80 에서 jiwoo(A4)와 seoyeon(A5)이 출장 · 외근 중에 접속했는데, 조사해 보니 모두 정상 접속이었습니다.
- 고칠 파일: `tuning.py` (`TRUSTED_IPS` 와 `apply_exception`)
- 어떻게 고치나요: 새로 넣고 뺍니다. 믿는 IP 리스트에 `203.0.113.80` 한 개를 넣고, `SaaS 평소와 다른 IP` 규칙의 알림 가운데 그 IP 에서 온 것만 알림 표에서 뺍니다. 다른 규칙의 알림(A3 · A6)은 같은 IP 여도 빼지 않습니다.
- 고친 뒤 확인: 오탐이 4개에서 2개로 줄었는지 보고, 빠진 알림 가운데 진짜 문제(`real` 이 `True`)가 0개인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.80 이 협력사 사무실 IP 가 맞는지 출장 · 외근 일정과 비교해 확인합니다.

#### 상황 6 · 로그인 규칙이 낸 알림이 평가에서 빠짐 (본보기)
- 원인: 데이터 문제입니다. 로그인 규칙이 낸 알림 A8 은 `login_alerts.json` 에 따로 저장돼 있고, 첫 평가에 쓴 `review_alerts.json` 의 알림 7개에는 들어 있지 않습니다. 평가는 알림 7개만 보고 「알림이 난 진짜 문제」를 세므로, A8 이 가리키는 P4 가 미탐으로 셉니다. 규칙은 알림을 이미 냈지만 평가에 들어가지 못했습니다.
- 고칠 파일: `final_check.py` (`merge_alerts`)
- 어떻게 고치나요: 새로 넣습니다. `pd.concat([alerts, login_alerts])` 로 두 알림 표를 위아래로 이어 붙인 뒤 합친 표로 평가합니다. A8 은 조사해 보니 진짜 문제(`real` 이 `True`)여서 오탐은 늘지 않습니다.
- 고친 뒤 확인: 미탐이 2개(P4 · P5)에서 1개(P5)로 줄고 오탐은 2개 그대로인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.50 이 로그인에 성공한 뒤 요청한 `/admin` · `/admin/users` 가 모두 403(접근 거부)이었는지, 그 뒤에도 요청이 이어졌는지 로그에서 확인합니다.

#### 상황 7 · 정산 조회 시도에는 알림이 나지 않음
- 원인: 현재 규칙은 사용자별 서버 실패가 3번 이상일 때 주로 알림 대상으로 삼습니다. seoyeon의 `SETTLE:QUERY`는 권한 없는 단 한 번의 시도라 횟수 기준에 걸리지 않았습니다.
- 고칠 파일: `access_detection.py` (탐지 대상 선택)와 관련 테스트
- 어떻게 고치나요: 정산 조회처럼 민감한 자원에 대한 「권한 없음」은 한 번만 발생해도 별도 알림 대상으로 두고, 그 외 반복 실패 규칙은 유지합니다.
- 고친 뒤 확인: `SETTLE:QUERY` 한 건이 탐지되고, 일반 실패 1회가 모두 불필요하게 알림으로 늘어나지 않는지 테스트합니다.
- 담당자가 가장 먼저 할 일(선택): 요청 계정·시각·거절 이유를 확인하고, 정당한 업무 요청인지 담당자에게 확인합니다.

#### 상황 8 · 서버가 같은 네트워크에 열려 있고, 지우면 접속 기록도 사라짐

- 고친 뒤 확인: 허용되지 않은 네트워크에서 접속할 수 없고, 컨테이너를 삭제·재생성해도 기존 접속 기록이 남는지 확인합니다.
