# 3과목 총정리 (학습자 · 2026-11-02(월))

## 상황 1 · 새 직원이 들어옴
- 원인: 데이터 문제입니다. hana가 입사했는데 `users.json`에 아직 등록되어 있지 않습니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: hana를 맡은 업무에 맞는 역할과 `"employed": true`로 추가합니다. 역할이 실제 업무에 맞는지 확인합니다.
- 고친 뒤 확인: hana의 요청을 다시 판정해 등록되지 않은 사용자 거부가 사라지고, 그 역할에 없는 권한은 여전히 거부되는지 확인합니다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴
- 원인: 퇴사자 정보가 정리되지 않았습니다. `employed`가 `true`이면 요청이 허용될 수 있고, `false`여도 계정이 남아 있으면 반복 시도와 점검 경고가 계속됩니다.
- 고칠 파일: `config/users.json`, 퇴사자 예외가 있으면 `config/exceptions.json`
- 어떻게 고치나요: 먼저 `employed`를 `false`로 바꿔 접근을 차단하고, 남은 계정과 그 사용자에게 발급된 예외를 정리합니다.
- 고친 뒤 확인: 요청이 거부되고, 계정과 예외 점검에서 더 이상 퇴사자의 항목이 나오지 않는지 확인합니다.

## 상황 3 · 다른 팀 업무를 잠시 지원함
- 원인: 영구 역할이 아니라 기간이 한정된 업무상 필요입니다. 예를 들어 seoyeon이 월말 정산 대조를 잠깐 지원합니다.
- 고칠 파일: `config/exceptions.json`
- 어떻게 고치나요: 승인된 최소 권한만 만료 시각과 사유를 붙여 예외로 추가합니다. 지원이 끝나면 만료된 예외를 목록에서 정리합니다. 업무 자체가 영구히 바뀐 경우에는 예외를 반복 연장하지 말고 `config/users.json`의 역할을 변경합니다.
- 고친 뒤 확인: 만료 전에는 예외로 허용되고 만료 시각부터는 거부되는지, 끝난 예외가 점검에서 제거됐는지 확인합니다.

## 상황 4 · 새 권한이 필요함
- 원인: 권한 요청·승인·부여 절차가 없으면 담당자가 파일을 직접 바꾸게 되어 승인자와 사유가 남지 않습니다.
- 고칠 파일: `req_create.py`, `req_review.py`, `req_grant.py`
- 어떻게 고치나요: 요청서를 만들고, 요청자가 아닌 승인자가 검토한 뒤, 승인된 요청만 정책과 현재 사용자 상태를 다시 확인해 예외로 부여합니다. 만료 시각은 필수로 둡니다.
- 고친 뒤 확인: 요청 상태가 `reviewing`에서 `approved`, `granted`로 바뀌는지와 거부·퇴사·이미 허용된 요청이 잘못 부여되지 않는지 확인합니다.

## 상황 5 · 안 쓰는 권한이 쌓임
- 원인: 부여 후 사용 여부와 업무상 필요성을 재검토하지 않아 오래된 권한이 남습니다. 사용 이력 없음만으로 불필요하다고 단정할 수는 없습니다.
- 고칠 파일: 점검은 `review_unused.py`와 `config/access_log.json`, 회수 제외 사유는 `config/exclude_list.json`
- 어떻게 고치나요: 90일 초과 미사용 권한을 후보로 만들고 담당자가 필요성을 확인합니다. 불필요한 권한은 회수 대상으로 보내고, 결산이나 사고 대응처럼 드물지만 필요한 권한은 사용자·권한·이유를 기록해 제외합니다. 퇴사자의 권한은 제외하지 않습니다.
- 고친 뒤 확인: 미사용 후보·회수 대상·제외 항목이 각각 의도한 목록에 들어가고, 예외 제외 사유가 재검토 가능한지 확인합니다.

## 상황 6 · 민감한 권한을 회수해야 함
- 원인: 권한은 불필요해졌지만 회수 방법과 영향 범위가 다릅니다. 쓰기 권한이나 역할 전체 해제는 업무 중단을 일으킬 수 있습니다.
- 고칠 파일: 예외 권한은 `config/exceptions.json`, 역할 권한은 `config/roles.json`, 퇴사자 역할은 `config/users.json`; 승인 상태는 `revoke_approve.py`
- 어떻게 고치나요: 먼저 회수 계획에서 대상과 영향을 확인합니다. 민감한 권한 또는 영향이 2건 이상인 계획은 승인을 받고, 승인 대기는 실행하지 않습니다. 승인된 계획만 실행하고 결과를 `config/revocation_log.json`에 남깁니다.
- 고친 뒤 확인: 전후 판정, 실행·대기 건수, 저장한 이력의 내용과 건수를 확인합니다.

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨
- 원인: 조건 규칙이 빠졌거나 실제 업무와 맞지 않을 수 있습니다. 규칙이 없으면 위험한 요청이 통과할 수 있고, 너무 좁으면 정상 직원도 거부됩니다.
- 고칠 파일: `config/conditions.json`
- 어떻게 고치나요: 시간과 위치 조건을 업무 필요에 맞게 추가하거나 조정합니다. 예를 들어 `SALES:CHANGE`에 업무 시간과 office·VPN 조건을 적용하고, gaeun의 실제 VPN 업무가 확인되면 `ACCOUNT:CHANGE`에 VPN을 허용할지 검토합니다. 외부 접속을 무조건 허용하거나 종료 시각을 검증 없이 늘리지 않습니다.
- 고친 뒤 확인: 새벽·외부 요청은 거부되고 승인된 업무 시간·위치 요청은 허용되는지, 경계 시각과 다른 요청에도 부작용이 없는지 테스트합니다.

## 상황 8 · 매주 어긋남을 확인해야 함
- 원인: 수작업 집계는 기준이 달라지거나 누락될 수 있고, 로그가 비어 있어도 거부율이 0%처럼 보일 수 있습니다.
- 고칠 파일: `checklist.py`, `log_summary.py`, `weekly_report.py`, 기준은 `config/alert.json`; 서버와 로그 수집도 함께 확인합니다.
- 어떻게 고치나요: 점검·요청 로그·거부율·경고를 같은 기준으로 모아 주간 보고서를 만들고, 요청 수가 0이면 안전으로 처리하지 말고 서버와 로그 수집 상태를 점검합니다. 경고 기준은 근거를 기록해 조정합니다.
- 고친 뒤 확인: 보고서의 요청 수와 허용·거부 수, 거부 사유, 점검 실패 및 조치 대상이 원본 로그와 일치하는지 확인합니다.
