## 2교시 · 도커로 서버 알림 세 건 직접 확인 · 보안 담당에게 답장

### 문제 2-1 · 알림 A 확인 — 서버 두 대로 열려 있는지 재고, 설정 값 · 비밀번호 · 실행 사용자까지 점검하기

- (가) `docker ps` 의 `PORTS` 열에서 두 서버가 각각 어떻게 나왔는지 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 PORTS 값 ② open-web-8082 의 PORTS 값
  - 답: `closed-web-8081` 은 `127.0.0.1:8081->80/tcp`, `open-web-8082` 는 `0.0.0.0:8082->80/tcp` 로 나왔다. 앞 서버는 이 PC에서만 접속할 수 있고, 뒤 서버는 모든 네트워크 인터페이스에 포트를 공개한다.
- (나) 🔍 `내주소` 로 접속했을 때 `closed-web-8081` 과 `open-web-8082` 의 결과(응답 번호)를 각각 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 응답 번호 ② open-web-8082 의 응답 번호
  - 답: 실제 LAN 주소를 넣은 접속 결과는 아직 확인하지 못했다. `http://내주소:8081` 처럼 글자 그대로 입력한 결과는 `000` 이었고, 8082 확인 명령은 `.curl` 오타로 실행되지 않았다. `127.0.0.1` 로는 두 포트 모두 `200` 이었다. 포트 설정상 실제 LAN IPv4 주소로 확인하면 8081 은 `000`, 8082 는 `200` 이 예상된다.
- (다) 🔍 `closed-web-8081` 은 `127.0.0.1` 로 접속하면 열려 있는데 `내주소` 로는 거부되는 이유는 무엇인가요? 다른 PC가 접속하는 경우와 어떻게 같은가요?
  - 쓸 내용: ① 127.0.0.1 로는 열리는 이유 ② 내주소로는 거부되는 이유 ③ 다른 PC가 접속하는 경우와 같은 점
  - 답: `127.0.0.1` 은 이 PC 자신을 가리키며, `closed-web-8081` 은 `127.0.0.1:8081` 에만 바인딩되어 있어 이 주소로 접속하면 `200` 이 나온다. 다른 인터페이스의 IP 주소로 들어오는 연결은 이 포트 바인딩에 포함되지 않아 접속할 수 없다. 다른 PC가 이 PC의 LAN 주소로 접속하는 경우도 같은 이유로 거부된다.
- (라) 🔍 사내 PC에서 접속되면 안 되는 관리용 서버를 켠다면 `-p` 를 어떻게 쓰고, 이것이 4일 차의 어떤 원칙과 같은가요?
  - 쓸 내용: ① -p 에 쓸 형태 ② 같은 생각을 말하는 4일 차 원칙
  - 답: `-p 127.0.0.1:호스트포트:컨테이너포트` 형태로 바인딩해 이 PC에서만 접속하게 한다. 필요한 통신만 허용하고 나머지는 막는 4일 차 방화벽의 최소 허용(allowlist) 원칙과 같다.
- (마) 🔍 `docker inspect` 결과에서 두 서버의 `HostIp` 는 각각 무엇이고, `PORTS` 열의 어느 표시와 같은 뜻인가요?
  - 쓸 내용: ① closed-web-8081 의 HostIp ② open-web-8082 의 HostIp ③ 각각 `PORTS` 열의 어느 표시와 같은 뜻인지
  - 답: 이번 실행 기록에는 두 컨테이너를 대상으로 한 `docker inspect` 결과가 없다. 포트 설정으로 예상되는 값은 `closed-web-8081` 의 `HostIp` 가 `127.0.0.1` 이고 `127.0.0.1:8081->80/tcp` 와 일치하며, `open-web-8082` 의 `HostIp` 는 `0.0.0.0` 이고 `0.0.0.0:8082->80/tcp` 와 일치한다. 실제 inspect 결과로는 확인하지 않았다.
- (바) 🔍 `open-web-8082` 의 비밀번호가 `docker exec` 로 그대로 읽혔습니다. 왜 문제이고, 비밀번호를 환경변수에 넣을 때 어떻게 다뤄야 하나요?
  - 쓸 내용: ① 읽힌 값 ② 왜 문제인지 ③ 다룰 때 지킬 것 두 가지 이상
  - 답: 이번에 실행한 `open-web-8082` 명령에는 `DB_PASSWORD` 환경변수를 넣지 않았고, `docker exec` 도 실행하지 못했으므로 읽힌 비밀번호 값은 없다. 환경변수로 비밀번호를 넣으면 컨테이너 접근 권한이 있는 사람이 값이나 설정을 읽을 수 있어 노출 위험이 있다. 실제 비밀번호를 코드·이미지·저장소에 기록하거나 커밋하지 않고, 필요한 컨테이너에만 전달하며, 운영 환경에서는 Docker secrets 또는 클라우드 비밀 관리 기능을 사용한다. 실습 예시의 `dev-pass-1234` 는 연습용 값이다.
- (사) 🔍 `whoami` 결과는 무엇이고, 이 서버가 침해되면 왜 위험이 커지나요? 6일 차 최소권한과 어떻게 이어지나요?
  - 쓸 내용: ① whoami 결과 ② 위험이 커지는 이유 ③ 최소권한과 이어지는 점
  - 답: 이번 실행 기록에는 `whoami` 결과가 없다. 실습의 Nginx 컨테이너에서 확인할 때는 `docker exec open-web-8082 whoami` 를 실행해야 하며, 기본 실행 사용자 `root` 가 확인되면 침해 시 공격자가 높은 권한으로 파일·설정 변경 등 큰 피해를 낼 수 있다. 필요한 권한만 부여해야 한다는 6일 차 최소권한 원칙에 따라, 서비스는 가능한 한 관리자(root)가 아닌 제한된 사용자로 실행해야 한다.

### 문제 2-2 · 알림 B · C 확인 — 응답이 없는 서버와 연달아 남은 404 읽기

- (가) 🔍 `wrongport-web-8084` 가 `Up` 인데 응답이 `000` 인 원인은 무엇인가요? `PORTS` 값, `docker logs` 에 요청 줄이 있었는지, `compare-web-8085` 와 비교한 결과를 근거로 적어 주세요.
  - 쓸 내용: ① 원인 ② `PORTS` 값 ③ `docker logs` 에 요청 줄이 있었는지 ④ `compare-web-8085` 와 비교한 결과
  - 답: 원인은 nginx 가 컨테이너 안에서 기다리는 포트가 `80` 인데 `-p 8084:8080` 으로 컨테이너의 `8080` 포트에 연결한 것이다. `docker ps` 에서는 상태가 `Up`, `PORTS` 는 `0.0.0.0:8084->8080/tcp` 로 나왔으며, `docker logs wrongport-web-8084` 에는 시작 메시지만 있고 요청 줄은 없었다. 비교 서버는 `0.0.0.0:8085->80/tcp` 로 연결되어 응답이 `200` 이었고, 로그에도 `"GET / HTTP/1.1" 200` 이 남았다. 따라서 8084는 서버가 꺼진 것이 아니라 컨테이너 포트 연결이 잘못된 장애이며, `-p 8084:80` 으로 다시 실행해야 한다.
- (나) 🔍 `probe-web-8087` 의 접속 기록은 장애 · 위협 · 접근통제 중 무엇인가요? 출처 · 시각 · 경로 · 프로그램 중 세 가지 이상을 근거로 적고, 10/19(월)의 `favicon.ico` `404` 와 무엇이 다른지 적어 주세요.
  - 쓸 내용: ① 유형 ② 근거 세 가지 이상 ③ `favicon.ico` 404 와의 차이
  - 답: **위협(경로 탐색) 의심**으로 분류한다. 로그에는 출처 `172.17.0.1` 에서 `2026/10/21 06:35:59` 에 `/admin`, `/login`, `/.env`, `/wp-login.php`, `/backup.zip` 을 연달아 요청한 기록이 있고, 사용자 에이전트는 `curl/8.21.0` 이다. 다섯 경로는 관리자 화면·로그인·환경 설정·백업 파일을 찾는 형태이고, 각 요청은 `404` 였으며 `/index.html` 요청만 `200` 이었다. 반면 10/19의 `favicon.ico` 404는 브라우저가 보내는 아이콘 파일 요청으로, 한 경로에 대한 일반적인 요청이었다. 이번 기록은 같은 출처·같은 초에 민감한 경로 여러 개를 자동 도구로 연속 탐색한 점이 다르다. 다만 실습 로그의 `172.17.0.1` 은 Docker 네트워크 쪽 주소이므로 실제 요청자의 신원이라고 단정하지 않고, 실제 서버라면 원본 출처와 관련 로그를 추가 확인한다.

  - 쓸 내용: A · B · C 마다 ① 유형 ② 확인한 근거(`PORTS` 값 · 응답 번호 · 기록 줄) ③ 먼저 할 일
  - 답:
